# Aadati — Engineering Rules

These are the concrete, decided conventions this project follows — established through actual refactoring work, not a generic checklist. Every rule here has a specific reason behind it (traced in `REFACTORING_LOG.md` where it's a significant decision). Use this as the reference while writing new code (Controllers, Caching, AOP, etc.) so new work stays consistent with everything already refactored.

## 1. Layering — Who Talks to Whom

- **Services work with Entities, not DTOs.** A service method's parameters and return types are Entities (or IDs/primitives), never Request/Response DTOs — with one deliberate exception below.
- **Exception: partial-update methods.** An `update` method that merges a request into an existing entity legitimately takes the Request DTO (`updatePercentageWeek(UUID id, PercentageWeek data)`-style, or `mapper.update(request, ..., @MappingTarget entity)`), because the "load existing, merge changes" logic is the service's job and the DTO is the natural shape of "what changed."
- **Controllers do DTO ↔ Entity mapping**, via injected MapStruct mappers — this is a Controller responsibility (HTTP/presentation concern), not "extra work Controllers shouldn't do." Simple mapping calls belong directly in the Controller; only genuinely complex reactive composition (not applicable to this blocking-style project) would justify a separate Converter layer.
- **Mappers never touch the database or call services.** A mapper transforms shapes; a service resolves IDs to entities (e.g. fetching a `HabitCategory` by ID) before handing it to a mapper as a parameter.
- **Service-to-service calls use Entities**, never DTOs — no reason to convert data shape between two backend components that already trust each other.

## 2. Repository Rules

- **Prefer** `UUID xId` **parameters over full related entities** when a query only needs identity comparison (e.g. `findAllByUser_UserId(UUID userId, ...)` instead of `findAllByUser(User user, ...)`). This avoids an unnecessary entity lookup before the query runs, since the Security Context (or another entity you already hold) usually already has the ID.
  - **Exception:** if a query genuinely needs a field from the related entity beyond its ID, accept the full entity instead — don't force this pattern where it doesn't fit.
- `JOIN FETCH` **only for relationships the caller will actually read afterward.** Don't fetch-join proactively "just in case" — it increases query cost for no benefit if the data is never used.
- **Never combine more than one** `@OneToMany`**/**`@ManyToMany` **fetch-join in a single query** — this throws `MultipleBagFetchException` (or silently produces a cartesian product in `COUNT` queries). `@ManyToOne`/`@OneToOne` fetch-joins have no such limit. If two to-many collections are genuinely needed together, split into two queries.
- **Partial-text search:** always `LOWER(field) LIKE LOWER(CONCAT('%', :param, '%'))` — never the non-standard `LIKE %:param%` syntax.
- **Exact-value fields (enums, fixed values) use** `=`**, never** `LIKE`**.** `LIKE` is for genuine free-text search only.
- `COUNT()` **queries return primitive** `long` (never `null`). `AVG()` **queries return** `Double` (nullable — resolve to a safe default like `0.0` inside the service, not left for the caller to handle).
- **Merge boolean-condition method pairs** (`findCompleted...`/`findUncompleted...`) into one method taking the boolean as a parameter, rather than two near-duplicate methods.
- **Update methods with a uniqueness constraint exclude the record being updated**: `existsByFieldAndIdNot(value, currentId)`, so a record's own unchanged field never triggers a false "already exists" against itself.
- **Dynamic/optional filters combined with** `AND` **use the** `(:param IS NULL OR field = :param)` **pattern** — combining optional filters with `OR` breaks the null-passthrough logic (a `null` parameter must never make the whole `WHERE` clause vacuously true).
- **Every derived method name must match the entity's actual property names exactly** (`whateverField`, not an abbreviated/renamed version) — Spring Data parses these literally and fails at startup otherwise. `And`/`Or` in a method name are parsed left-to-right into nested groups, not by normal SQL operator precedence — verify complex combined names actually mean what they look like they mean, or write an explicit `@Query` instead.

## 3. Exception Handling

- **Six exception types, one HTTP status each**, classified by *who's at fault*, not by entity: `ResourceNotFoundException` (404), `DuplicateResourceException` (409), `InvalidRequestException` (400), `BusinessRuleViolationException` (422), `InvalidCredentialsException` (401), `OperationFailedException` (500). Don't create a new exception type per entity (`HabitNotFoundException`, `RoleNotFoundException`, etc.) — that's the same category duplicated for no reason.
- **Responses use** `ProblemDetail` **(RFC 7807)** via a single `GlobalExceptionHandler`.
- **Server-side failure messages (500-class) return a fixed generic message**, never the raw exception message — log the real message server-side instead. Client-facing exceptions (404/409/400/422/401) return their message as-is, since it was authored to be read by the API consumer.
- **Race-condition-safe uniqueness**: rely on the database's unique constraint as the actual enforcement (`try { save() } catch (DataIntegrityViolationException) { throw DuplicateResourceException }`), not a check-then-act pre-check alone — or combine both only if the pre-check adds genuine UX value beyond what the constraint catch already provides.
- **Filters run before** `DispatcherServlet`**.** Any exception thrown inside a `Filter` (JWT parsing, `UserDetailsService` lookups performed there) must be caught *inside the filter itself* — `@RestControllerAdvice`/`GlobalExceptionHandler` cannot see it, no matter what exception type it is.

## 4. Service Layer Conventions

- **Class-level** `@Transactional(readOnly = true)`, with individual write methods (`create`/`update`/`delete`) explicitly overriding with `@Transactional`.
- **One private** `getXOrThrow(id)` **helper per service**, used everywhere that entity needs to be loaded or confirmed to exist — never repeat `existsById` + separate query.
- **Domain invariants live in the entity, not duplicated in the service.** If an entity has a domain method enforcing a rule (`PercentageDay.updateRate()` validating 0–100), the service calls it and trusts it — it does not re-validate the same rule itself.
- `@RequiredArgsConstructor`**, not** `@AllArgsConstructor`, on Spring-managed beans — avoids silently absorbing a future non-final field into the constructor.
- **Naming reflects actual behavior.** `search...` implies partial matching — don't use it for exact-match lookups. A method that computes something (`resolveGradeText()`) shouldn't be named like a plain getter (`getGrade()`).

## 5. What NOT to Build (Rejected Speculative Complexity)

Don't add infrastructure for a scenario that doesn't exist in this project yet. Rejected so far, with reasoning:

- `createdBy`/`updatedBy` auditing — no admin-edits-another-user's-data scenario exists.
- A dedicated rate-limit exception — `bucket4j` is a dependency but no rate limiting is actually implemented.
- Roles duplicated inside JWT claims — `UserDetailsService` is called on every authenticated request regardless (for `UserDetails` construction), so the claim added no realized performance benefit and risked staleness.
- Caching the refresh-token validation — would turn a deliberately stateless JWT scheme partially stateful for no identified problem.

If a similar "would this be nice to have" idea comes up for Controllers/Caching/AOP, ask first: *is there an actual, current need, or is this solving a hypothetical?*

## 6. Refactoring Process Rules

- **One architectural layer at a time.** Changing Entities, DTOs, and Mappers simultaneously caused a cascade of hard-to-trace compile errors early in this project. Finish Entities, then DTOs, then Mappers, then Repositories, then Services, then Controllers — don't mix layers mid-change.
- **Verify before deleting.** Before removing anything that looks unused (a method, a class, a config value), `grep` the codebase to confirm — a "clearly unused" Builder constructor turned out to be load-bearing more than once in this project.
- **Every non-trivial decision is logged in** `REFACTORING_LOG.md` with Problem / Decision / Why / Impact, and a real source (official docs, RFC, OWASP) where one exists — not "it felt right."

## 7. Security & Config

- **No secrets in source, ever** — environment variables only, with **no hardcoded fallback default** for anything sensitive (a fallback defeats the purpose: the app should fail to start rather than run with a known/leaked value).
- **Admin access is limited to aggregate statistics for personal data** (counts, not raw browsing via partial-match search or unbounded full-table reads) — data minimization applies to internal/admin tooling too, not just public endpoints.
- **Cleanup job retention is sized to each entity's actual growth rate** — fast-accumulating entities (daily completion records) get short retention (~180 days); slow-growing entities (`HabitWeek`, `HabitCategory`) need no cleanup at all. One-size-fits-all retention is a red flag.

## 8. DTOs & Mapping

- **Prefer Java records over mutable Lombok classes** for Request/Response DTOs. Use Lombok `@Builder` directly on a record when a fluent constructor is needed for a DTO with many fields — records and Lombok builders are not mutually exclusive.
- **MapStruct** `@Mapper` **interfaces, not hand-written static mapper classes** — if MapStruct is a declared dependency, it should actually be used via `@Mapper(componentModel = "spring")`, not reimplemented by hand.
- **System-managed fields (**`id`**,** `createdAt`**,** `updatedAt`**) are** `@Mapping(..., ignore = true)` in mappers — let entity lifecycle/auditing set these, never a mapping `expression`.
- **Relationship fields written by an `update()` mapper are decided by whether the entity enforces a rule on that field, not by whichever fix silences the MapStruct compile error:**
  - **Structural relationships with no business rule on reassignment** (e.g. `HabitTask.taskPriorityLevel`, `HabitTask.habitCategory`, `HabitCalendar.habitWeek`, `TaskCompletion.habitTask`/`habitCalendar`, `HabitCompletion.habit`/`habitCalendar`) — the service resolves the ID to the entity and passes it into the mapper's `update(request, resolvedEntity, @MappingTarget entity)` method as a parameter (per Rule 1: mappers never call services, but do receive service-resolved entities). This requires a write accessor, so add a **field-level `@Setter`** on that specific field — never a class-level `@Setter`/`@Data` on the whole entity, and never reach for `@Mapping(..., ignore = true)` here, since that would just defer the same write-access requirement to the service without adding any protection.
  - **Fields with an entity-enforced business rule on reassignment** (e.g. `PercentageDay.rate` validated by `updateRate()`, `HabitCompletion.complete` guarded by `markComplete()`/`markIncomplete()`) — keep the field setter-less. The mapper marks it `@Mapping(target = "x", ignore = true)`, and the service calls the entity's domain method directly after the mapper runs. Never add a `@Setter` here just to make MapStruct's automatic mapping succeed — that bypasses the entity's own validation and re-creates an anemic model for that field.
  - **The test to apply:** does this field have a named domain method enforcing an invariant when it changes? If yes → no setter, mapper `ignore`s it, service calls the domain method. If no → field-level `@Setter`, let the mapper set it directly. Never choose between the two options based on "whichever one compiles" — that produces the same error resurfacing later as a validation bug on a business-rule field.

## 9. Pagination

- `PageableUtils` **is the single source of pagination defaults/bounds** (default page size, max page size, default sort field) — services don't construct `PageRequest` directly.
- **Client-controlled inputs (**`pageNumber` **from a request) get defensive validation** (clamped to non-negative). **Service-decided values (**`pageSize`**,** `sortBy` **fixed internally)** get validation too, but as a cheap safety net against a future coding mistake — not because they're exposed to untrusted input.

## 10. AOP — Cross-Cutting Logging

- **Scope is limited to logging only** (method entry/exit, execution time, failure logging) on the service layer, via a single `@Aspect` with one `@Around` advice on `execution(* com.mts.aadati.services.*.*(..))`. This is not a general-purpose AOP adoption — business logic, validation, and security concerns stay in their existing dedicated layers (services, `@RestControllerAdvice`, Spring Security). Don't add a second aspect for a new cross-cutting concern unless there's an actual, current need (same test as Section 5).
- **A logging aspect must never be able to break the underlying call it's wrapping.** Anything the aspect does to build its log line (reading `SecurityContextHolder`, casting the principal, etc.) must be wrapped so it degrades to a safe fallback value instead of throwing — especially since this pointcut also covers calls with no authenticated user in context (`AuthenticationService.login()`/`register()` themselves, and any `@Scheduled` job). Resolving log context happens in a small helper that catches its own exceptions internally; it is never allowed to throw before `joinPoint.proceed()` is reached.
- **Never log raw method arguments or return values by default.** Several service methods take or return DTOs/entities carrying passwords, tokens, or other PII (`AuthenticationService.register`/`login` being the clearest case) — logging `Arrays.toString(args)`/`result` unconditionally risks writing secrets straight into the log stream (CWE-532). Log method signature, resolved user id, and timing only; if argument-level tracing is ever genuinely needed, it requires an explicit per-DTO allow-list/masking approach, not a blanket dump.
- **Give the logging aspect an explicit `@Order` that places it outside `@Transactional`** (e.g. `@Order(Ordered.HIGHEST_PRECEDENCE)`), since both are proxy-based advice on the same beans and the ordering between two aspects with no explicit `@Order` is not guaranteed. Wrapping outside the transactional advice means the aspect's "Exiting" log reflects the actual committed outcome (including a commit-time failure), not just the raw method return before commit/rollback.
- **Verify the pointcut's package expression against the real package name before trusting it compiles/matches anything.** An `execution(..)` pointcut that doesn't match the actual package silently advises nothing — no startup error, just zero log coverage — which is easy to miss without deliberately checking a known method actually gets logged.
- **Reading `SecurityContextHolder` inside the logging aspect is observability, not security enforcement** — it consumes an identity Spring Security already resolved earlier in the request, purely for log correlation (this is standard practice per the OWASP Logging Cheat Sheet, which lists "who" as a core field for security-relevant log events). It's a fundamentally different concern from a persisted audit trail (`createdBy`/`updatedBy`, already rejected in Section 5): nothing here is stored or queried against, it only lives in an ephemeral log line. The aspect must never cross into making an authorization decision — `hasRole()`/`hasAuthority()` checks, throwing `AccessDeniedException`, or gating method execution based on identity — that stays exclusively in Spring Security.

## 11. Caching

- **The Layering rule (Section 1) is not renegotiated for caching's sake.** Services still work with Entities, not DTOs — including when a service method is `@Cacheable`. Caching sits *inside* the service layer, before any Controller-side DTO mapping ever runs, so it is not a valid reason to change what a service returns; it's a reason to control what gets serialized at the entity level instead.
- **Sensitive entity fields are `@JsonIgnore` at the field level, independent of caching.** If a field must never leave the service layer in any serialized form (e.g. `User.password`), mark it so on the entity itself, rather than reshaping the service's return type. This protects every serialization path (cache, accidental logging, future features), not just Redis.
- **A `@JsonIgnore`d field comes back `null` on a cache hit — because it was never serialized into the cached value in the first place.** Any lookup path that needs the *real* value of that field for its own logic (e.g. comparing a submitted password against `User.password` during login/credential verification, or any future "verify old password" flow) must never be `@Cacheable` — it queries the repository directly. Applying `@Cacheable` to that lookup wouldn't fail loudly; it would silently break credential checks for every cache hit after the first, which is worse than not caching at all. The test to apply before caching any method touching a `@JsonIgnore`d field: *does this specific call site need the real value, or just the rest of the entity?* If it needs the real value, it's excluded from caching, the same way `HabitCompletion`/`TaskCompletion` are excluded — just for a correctness reason here instead of a churn-rate one.
- **Only `@Cacheable` a query whose entity graph is already fully, eagerly initialized** (i.e. the relevant `@ManyToOne`/`@OneToOne` relationships are already `JOIN FETCH`-ed per the Repository Rules in Section 2). Never cache an entity with an uninitialized lazy relationship — serializing a lazy Hibernate proxy outside its persistence context throws `LazyInitializationException` or silently produces wrong data, and the object returned from cache on a hit is a detached POJO that needs an explicit `repository.save(...)` if mutated, not JPA dirty-checking.
- **`CacheTtl` (paired with `CacheNames`) is the single source of truth for per-cache TTL policy** — the same "one centralized source, no ad-hoc values scattered across the codebase" pattern already used for `PageableUtils` (pagination) and `Auditing` (timestamps). Services/config never hardcode a `Duration` for a specific cache inline; add or adjust an entry in `CacheTtl` instead.
- **Cache name constants live in `CacheNames`, not as inline string literals** — and are named after the entity they represent, unambiguously (e.g. `HABIT_DAY_WEEK`/`HABIT_WEEK`, not `DAY`/`WEEK`, to avoid visual collision with `PERCENTAGE_DAY`/`PERCENTAGE_WEEK`).
- **Cache applicability is decided by an entity's actual read/write ratio, the same lens already used for cleanup-job retention sizing (Section 7).** High-churn entities (`HabitCompletion`, `TaskCompletion` — daily completion toggles) are excluded from caching entirely rather than cached and immediately invalidated on every write; caching only pays off for read-heavy, comparatively stable data.
- **`RedisCacheManager` is built with `.transactionAware()`.** Every service method already runs inside a Spring-managed transaction (Section 4's class-level `@Transactional`), so without this, a `@CachePut`/`@CacheEvict` could write to Redis before the surrounding transaction commits — leaving the cache holding state for a write that was later rolled back. `.transactionAware()` defers the actual cache write/evict until after successful commit, and it does this at the `CacheManager` level, so it holds regardless of advisor ordering between `@Transactional` and the cache interceptor (unlike the AOP logging aspect in Section 10, which needed an explicit `@Order` to get the same guarantee).
- **Cache failures degrade gracefully — they are not the "swallow the error" anti-pattern rejected in Section 4.** A `CacheErrorHandler` that logs a `GET`/`PUT` failure and lets the call fall through to the database is correct: the cache is an optimization, not the source of truth, so a Redis outage costs performance, not correctness, and the caller still gets a real answer from the DB. This is categorically different from swallowing a business-logic failure and returning a fabricated empty/default result.
- **`EVICT`/`CLEAR` failures are logged at a higher severity than `GET`/`PUT` failures.** A failed eviction risks serving stale data for the rest of that key's TTL — a correctness risk, not just a performance one — so it's worth a louder log signal (`error`, not `warn`), even though the write itself is still allowed to succeed (Aadati's short TTLs on volatile data bound how long that staleness window can last).

## How to Use This Going Forward

When writing Controllers, Caching, or AOP code: before deciding how to structure something, check if a rule here already answers it. If a new situation doesn't fit any rule above, make the call, then **add it here** (or to `REFACTORING_LOG.md` if it's significant enough to need sourced justification) so the next piece of code follows the same decision.
